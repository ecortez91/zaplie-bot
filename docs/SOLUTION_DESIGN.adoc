== Overview

Zaplie (formerly Zapp.ie) is a Microsoft Teams application that lets teams send
each other Bitcoin micro-payments ("Zaps" of Sats) as recognition and reward.
It combines a conversational Teams bot, a set of React web tabs, and serverless
HTTP endpoints, all backed by an https://lnbits.com/[LNbits] Lightning wallet
and account system. Every Teams user is automatically provisioned with two
LNbits wallets: an *Allowance* wallet (a spending budget, funded with
`LNBITS_INITIAL_ALLOWANCE` when it is created) and a *Private* wallet (where
received Zaps accumulate).

== Component Design

=== Teams Bot

`src/index.ts` starts an Express server (default port 3978) and wires a
`CloudAdapter` with multi-tenant credentials. All turns pass through
`FetchUserMiddleware`, which resolves the Teams member and calls
`UserService.ensureUserSetup()` — creating the LNbits user (keyed by the AAD
object id stored in an LNbits extra field) and ensuring the Allowance and
Private wallets exist.

`src/teamsBot.ts` extends `TeamsActivityHandler`. Text commands are registered
in a static `SSOCommandMap` keyed by lower-case message text:

[cols="1,2,2"]
|===
| Command | File | Behaviour

| `send zap`
| `src/commands/sendZapCommand.ts`
| Presents an Adaptive Card (schema 1.5) with a multi-select recipient picker, message, and amount (1–10,000); on submit, pays each recipient and updates the card in place with results and remaining balance

| `show my balance`
| `src/commands/showMyBalanceCommand.ts`
| Lists the user's LNbits wallets with balances (msat/1000)

| `show leaderboard`
| `src/commands/showLeaderboardCommand.ts`
| Ranks users by Private wallet balance in an Adaptive Card

|===

`withdraw my zaps` is implemented as a stub in
`src/commands/withdrawFundsCommand.ts` but is deliberately *not* registered in
`SSOCommandMap` and not listed in the Teams manifests, so the bot never
advertises a command that cannot complete. See issue #293.

The bot also implements Teams SSO handlers (`handleTeamsSigninVerifyState`,
`handleTeamsSigninTokenExchange`). Conversation and user state use in-memory
`MemoryStorage`.

=== LNbits Integration

Three parallel clients speak to the LNbits REST API:

- `src/services/lnbitsService.ts` — bot-side (~20 exported helpers). Auth is
  either an `X-Api-Key` header (admin or wallet invoice key) or a Bearer token
  obtained from `POST /api/v1/auth` (cached at module level with concurrent
  request de-duplication). Uses the core API (`/api/v1/wallet`, `/payments`,
  `/wallets/{id}`) and the core Users API (`/users/api/v1/user`,
  `/users/api/v1/user/{id}/wallet`). Funds a new user's Allowance wallet once
  with `LNBITS_INITIAL_ALLOWANCE` (`topUpWallet`, called from `UserService`);
  recurring replenishment is not bot code (see Design Decisions).
- `tabs/src/services/lnbits/` — browser-side equivalent used by the tabs, split
  per concern (`auth`, `cache`, `users`, `wallets`, `payments`, `rewards`).
- `functions/services/lnbitsService.ts` — request-scoped variant; the LNbits
  base URL and credentials arrive with each HTTP request.

=== Web Tabs

Routes (`tabs/src/App.tsx`): `/feed`, `/users`, `/rewards`, `/wallet`,
`/settings` — all wrapped in `RequireAuth` (MSAL `acquireTokenSilent`, redirect
to `/login` on failure) — plus `/login`, `/auth-start`, `/auth-end`. Providers:
`MsalProvider` → `RewardNameProvider` → `PageLayout`.

[cols="1,3"]
|===
| Page | Purpose

| Feed
| Zap activity feed, activity chart, and total-Zaps statistics

| Users
| Directory of users with wallet information

| Rewards
| Rewards carousel / redemption view

| Wallet
| Private and Allowance wallet tabs: balance card, transaction history, allowance status

| Settings
| Administrator setting to rename "Sats" (the reward label)
|===

The reward label is persisted by the Express backend
(`GET/POST /api/reward-name` → `tabs/backend/data.json`) and consumed by both
the tabs (`RewardNameContext`) and the bot (`src/services/fetchRewardsName.ts`).

=== Azure Functions

Three anonymous HTTP triggers under `functions/` (compiled to `dist/`):
`getUsers`, `showUsers`, and `sendZap` (invoice-and-pay between two users'
wallets — the automation/Copilot entry point). LNbits credentials are supplied
per-request via HTTP Basic auth plus `siteURL`/`adminkey` query parameters.

== Data and State

[cols="1,2,2"]
|===
| Data | Where it lives | Notes

| Users and wallets
| LNbits (core Users API)
| Keyed by AAD object id in an extra field; one Allowance + one Private wallet per user

| Transactions / Zaps
| LNbits payments ledger
| Queried per wallet for feed, history, and leaderboard. Each zap carries an
  `extra` object `{ tag: 'zap', from, to }` where `from`/`to` are
  `{ id, name, user, displayName }` projections of the wallets, never the
  wallet objects themselves

| Reward label ("Sats")
| `tabs/backend/data.json`
| JSON file on the web server; no database

| Bot conversation state
| `MemoryStorage` (in-process)
| Ephemeral — lost on restart, not multi-instance safe
|===

== Design Decisions

=== Payment metadata is a projection, not the wallet

*Context:* LNbits stores the payment `extra` object as JSON on the payment
row. Anyone holding the receiving wallet's invoice key can read it, and the
portal feed loads it into every browser. Until this decision the bot wrote
the full sender Allowance and receiver Private `Wallet` objects there,
including `adminkey`, `inkey` and `balance_msat`.

*Decision:* Writers build `extra.from` and `extra.to` through
`toPaymentExtraWallet` (`src/services/paymentExtra.ts`), which picks
`id`, `name`, `user` and an optional `displayName` by name and throws when
the wallet is missing. No writer depends on the `Wallet` type for metadata.

*Consequences:* New payments carry no key material. Readers (portal feed,
automation summary, transaction log) already use only those fields.
Payments written before this decision cannot be rewritten through the
LNbits API; rotating the affected wallet keys is an operator decision.

=== LNbits as the wallet backend

*Context:* The system needs per-user custodial Lightning wallets with an
admin API.

*Decision:* Use LNbits with its core Users API rather than building a
ledger.

*Rationale:* Open source, self-hostable, proven Lightning integration, and a
REST API that supports programmatic user/wallet creation and payments.

=== Two wallets per user (Allowance vs Private)

*Context:* Users need both a budget to give from and a balance they have earned.

*Decision:* Provision each user an Allowance wallet (funded with
`LNBITS_INITIAL_ALLOWANCE` on creation) and a Private wallet (receives Zaps).

*Rationale:* Cleanly separates "money to give" from "money earned", enabling
leaderboards on Private balances and periodic replenishment without touching
earnings.

=== Scheduled top-ups are not bot code

*Context:* The bot carried a `scheduledTopup()` function that swept every
Allowance wallet into a host wallet and refunded it. Nothing on `main` ever
called it: the node-cron job that invoked it on the PR #73 branch was removed
on that branch (59c25967) before the squash merge (82f2fd1b). It read three
settings
(`LNBITS_HOST_WALLET_ID`, `LNBITS_HOST_USER_ID`, `LNBITS_INKEY`) used nowhere
else, and it ran its per-wallet payments in a fire-and-forget loop (PR #242
and PR #310 document the defects).

*Decision:* Remove it, per the Product Owner on PR #242 ("I think
`scheduledTopup` is deadcode if we're going to use the allowance extension for
LNbits?") and PR #310 ("Can still remove the dead code."). Recurring
allowance funding belongs to the LNbits
https://github.com/BenGWeeks/allowance[allowance extension], which pays to a
Lightning address on a schedule, so each Allowance wallet needs a Lightning
address before that can be wired up (tracked separately). The bot only funds
a wallet once, when it is created.

*Consequences:* No scheduler, host wallet or sweep logic lives in the bot.
The leaderboard keeps excluding payments whose memo contains
`Weekly Allowance cleared` so historical sweeps never count as zaps.

=== Teams Toolkit for provisioning

*Context:* The app spans an AAD app registration, a bot registration, an App
Service, and a Teams app manifest.

*Decision:* Drive provisioning and deployment through TeamsFx
(`teamsapp.yml` + `infra/azure.bicep`).

*Rationale:* Single declarative lifecycle for AAD, Bot Service, ARM resources,
and manifest packaging across local/dev environments.

== Known Limitations

- Bot state is in-memory; a restart clears conversation/user state.
- The reward-name API is guarded by a placeholder shared secret and a JSON
  file rather than a real datastore.
- The Azure Functions are anonymous at the platform level and receive LNbits
  credentials per request.
- The tabs app currently ships LNbits credentials (including an admin key) to
  the browser via `REACT_APP_*` variables — acceptable only for trusted
  internal deployments; see `SECURITY.md`.
